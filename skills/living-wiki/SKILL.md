# Живая память: MEMORY.md + skills (skill v2)

Один вход — `AGENTS.md`, одно хранилище — `MEMORY.md`, один тип процедур — `skills/<имя>/SKILL.md`. Никакого Obsidian, графа, `[[ссылок]]`, `wiki/`, `journal/`, `raw/`. Версия архитектуры — v2.

Установка: если `MEMORY.md` нет, создай его с пустым скелетом (раздел 2 в `AGENTS.md`) и работай дальше. Если есть — сверь `rules_hash` в frontmatter `AGENTS.md`: не совпал, сверь отличия с актуальным репозиторием (не перезаписывай автоматически при наличии локальных настроек); `MEMORY.md` и `skills/` не трогай.

## Как устроена память

- `MEMORY.md` — плоский список коротких фактов, разделы: «О пользователе», «Проект и стек», «Решения», «Грабли», «Открытые вопросы».
- Одна строка — один факт, декларативно: «пользователь предпочитает короткие ответы», а не «всегда отвечай коротко».
- Дубликаты не дописываются: похожая строка заменяется или сливается.
- Противоречие не хранится двумя версиями: старая строка заменяется новой.
- Лимит файла — 6000 символов (5400 — начинай сжимать). Подсчёт ведётся в Unicode-символах без `\r`. Для кириллицы ~11–12 КБ в UTF-8 — это норма. Проверка: `python scripts/living_wiki_cli.py check-size`.
- Профили объёма: компактный (6000 символов), стандартный (15000 символов) и расширенный (50000 символов для моделей с большим окном контекста).
- Догадка помечается `[вывод]`.

## Два слоя памяти

`MEMORY.md` — горячий слой (факты и строки-указатели, до 6000 символов), `memory/<тема>.md` — холодный слой (детали по областям: архитектура, контракты, схема БД, бизнес-правила).
- Плоская структура: вложенные папки внутри `memory/` запрещены. Для подтем используй плоские имена: `memory/<тема>-<подтема>.md`.
- Запрет викиссылок: используй стандартные ссылки Markdown `[Описание](memory/<тема>.md)`, викиссылки `[[...]]` строго запрещены.
- Один файл темы — до ~15 КБ (примерно 300 строк), читается только когда тема всплыла; больше — разбей на плоские подтемы.

## Когда не влезает (Переполнение)

6000 — потолок горячего файла, а не знаний. Строгий порядок, стоп на первом шаге, который дал место:

1. **Вытеснить кластер в тему**: если накопилось 3 и более связанных фактов по одной теме, вытесни весь кластер в `memory/<тема>.md`, оставив в `MEMORY.md` одну строку-указатель (`- Тема — memory/<тема>.md`).
2. **Иммунитет указателей**: строки вида `- Тема — memory/<тема>.md` никогда не удаляются при сжатии памяти.
3. **Слить дубликаты** и похожие факты.
4. **Убрать неактуальное**: починенные грабли, закрытые вопросы, отменённые решения.
5. **Инвертированный приоритет вытеснения**: стабильные статические факты («Проект и стек», «Решения») вытесняются в темы первыми; оперативные секции («Грабли», «Открытые вопросы») сохраняются в горячей памяти до последнего. Раздел «О пользователе» чистится только слиянием.
6. **Сжать формулировки**: убрать обоснования и примеры, оставить сухой факт.
7. **Не писать строку вообще**, если она не изменит поведение в следующей сессии.

## Как устроены скилы

`skills/<имя>/SKILL.md` с frontmatter `name`, `description` («Use when …»), `updated`, и разделами «Когда применять», «Шаги», «Грабли», «Проверка».

- Создавай, когда процедура повторилась, оказалась неочевидной или пользователь сказал «запомни, как делать».
- После задачи, где скил пригодился, допиши строку о том, чего не хватало. Подвёл дважды — перепиши «Шаги» целиком.
- Скил длиннее 150 строк — вынеси детали в `<имя>/details.md`, в шагах оставь ссылку.
- Индекса нет: список папок и есть индекс.

## Аудит ответа — при завершении содержательной задачи

Перед завершением содержательной задачи (написан код, выполнен рефакторинг, решена проблема, обновлена архитектура) молча проверь:
1. Новый факт о пользователе или проекте? → `MEMORY.md`.
2. Принято решение или найдена причина бага? → `MEMORY.md`.
3. Сложилась повторяемая процедура? → скил.
4. Старая запись устарела? → замени или удали.

**Гейт аудита**: на тривиальные вопросы, краткие реплики, уточнения и промежуточные шаги аудит не запускается. Ничего нового нет — не пиши ничего. Выдумывать записи ради активности запрещено.

## Многоагентность и безопасность

При одновременной работе нескольких агентов используй блокировку `MEMORY.md.lock` (TTL 15с) либо буферный журнал `memory/journal.log` для предотвращения потери данных при одновременных записях.

## Чистота

В корне проекта: файлы проекта + `AGENTS.md` + `MEMORY.md` (+ указатели инструментов). Второй памяти не заводить (`memory.md`, `notes.md`, `brain/`); найденную — перенести в `MEMORY.md` и удалить. Память — не журнал: только то, что действует сейчас.
